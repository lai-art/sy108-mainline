# 测速 与 流量消耗 — 方案

> 目标：在 SY108 的 LuCI 里做**两个独立功能**：① 测速 ② 流量消耗。
> 参考站：`net.netart.cn`、`llxh.huangyunkai.cn`、`llxs.youvip.cc`
> 版本：v3（2026-11-11）— 按用户拍板走 **B**；补入开源实现调研 §1.5、专业测速原理 §1.6；
> 按用户纠正"**流量消耗器和测速是两个东西**"把两者拆成独立功能（§1.6.3）

## 0. 一页结论

### 已定：按 B 走

测速与流量消耗都在**设备本地**执行，从 `wwan0` 出去，前端只负责下指令和显示。A2（直接部署 FlowLoss 浏览器版）**作废**。

原因是那条绕不过去的链路问题：浏览器发起的流量走的是「谁在跑浏览器」那条链路——PC 通过管理口上网时测到的是 `PC → 管理口 → 模组` 的最慢一段；PC 不走这台设备上网时，测的干脆是 PC 自己的宽带。而浏览器既绑不了 `wwan0`，也读不到模组温度。

### 而且：这是两个独立功能

> 用户纠正："流量消耗器和测速是两个东西。" v2 之前把它们当一个功能的两副面孔，是错的。

| | ① 测速 | ② 流量消耗 |
|---|---|---|
| 要的答案 | "这张卡能跑多快" | "我用掉多少流量" |
| 停止 | **自动**，≤30 s / ≤150 MB | 手动 / 1 GB 上限 / 300 s / 过热 |
| 结果主数 | **P90 下行带宽** | **累计消耗流量** |
| 误触成本 | 低 | **高，必须二次确认** |

**只共享底层**（服务、curl 编排、`rx_bytes` 采样、节点清单、三道保护、busy 守卫）；**参数、停止逻辑、结果语义、页面、确认流程各自独立**。前端是两个独立 tab，不共用"开始"按钮。详见 §1.6.3 / §1.6.4。

### 参考站源码已找到

`arsnyeon/FlowLoss_SpeedTestPanel`，**MIT 协议**，Vue 3 + Vite，三个站是同一产品的三代部署（§1.5）。它解决"前端怎么写"，不解决"测的是谁"；引擎算法与节点清单可作为实现参考，但**不做整体搬用**。

### 首版只做下行

上行需要可写端点，公共节点基本没有，强行做只能给出假数据（§4.3）。

### 1.5.3 引擎到底怎么跑（这才是可复用的部分）

核心只有 **`src/composables/useSpeedRunner.ts`，21 KB**，其余都是 UI。逻辑拆开是六件事：

| 机制 | 实现 | 对我们的价值 |
|---|---|---|
| **并发拉流** | `startThread(i)` 起 N 个 `while(isRunning)` 循环，每个循环 `fetch()` → `response.body.getReader()` 逐块读 | 结构简单，可直接翻译成 C 的多线程或 curl 多进程 |
| **字节计数** | `recordTransferBytes(Math.min(chunkLength, realLength - decodedLength))` | ⭐ **它用 `realLength` 截断**，防止服务端在 `Content-Length` 之外补 padding 时把脏字节算进流量。这个坑我们必须同样处理 |
| **限速** | `speedCtr()` 令牌桶：每线程每秒配额 = `maxSpeed / 8 / threadNum`，超了就 `setTimeout` 等到下一秒 | 可换成 `curl --limit-rate`，但要注意 `--limit-rate` 是整进程而非每线程 |
| **每秒采样** | `secEvent()`：`speed = (bytesUsed - recordUse) / (now - recordTime)`，同时 `setSpeed` 与 `addChartPoint` | 直接照抄 |
| **上限判定** | `frameEvent()` 每 **15 ms** 跑一帧，查 `bytesUsed >= maxUse` | 15ms 粒度意味着上限最多超 15ms 的流量，可接受 |
| **曲线压缩** | `addChartPoint()` 用自适应步长 `stepLength`：时长超过 `200 × stepLength` 就翻倍，上限 64 | ⭐ 长跑时曲线点数不爆炸，避免内存涨。我们的前端也要做 |
| **防缓存** | `fetchUrl += (有? ? & : ?) + '_=' + Date.now() + '.' + index` | 与三站一致，必做 |
| **节点轮换** | `checkRotation()`：`bytesThisRound >= trafficLimit × 1024 × 1024` 就切；`findNextRotationNode()` 跳过 `maxRuns` 已跑满的 | 逻辑干净，可照搬 |

另有两处工程细节值得记：`nodeRequest()` 调 `safeWebNodeHeaders()` **主动剥离自定义节点的敏感请求头**，剥了就提示"请改用 HTTPS"；`useBackgroundKeepAlive` 负责切标签页后继续跑。

### 1.5.6 它解决了什么，没解决什么

**解决了（能省人日）：**

- 前端 UI 从零变成"裁剪现成的"：曲线、节点选择器、线程数、流量/带宽上限、运行时长、峰值、出口 IP 全都有
- 引擎算法有了经过线上验证的参考实现（尤其字节截断、曲线压缩、轮换计数这三个坑）
- 节点源有了起点，不用凭空想

**没解决的（架构问题一个都没变）：**

- **它仍然跑在浏览器里。** `startThread()` 用的是 `fetch()`，出口是"打开页面的那台设备"的网络栈。用户在电脑上开 LuCI 测速，流量走 `电脑 → USB 管理口 → 壳 → wwan0`，慢的那一段照样是瓶颈
- **无法指定出口接口。** 浏览器拿不到 `wwan0` 绑定能力（这是 OS 层的能力，JS 没有对应 API）
- **读不到模组状态。** 它不知道温度、信号、QCI，也就无法做"超过 70 ℃ 自动停"（§4.5 那道保护）
- **不能后台跑。** `useBackgroundKeepAlive` 保的是"切换标签页不停"，不是"关掉页面还跑"
- **依赖外部节点存活。** 上面已经死了 2 个，谁来维护？

一句话：**它把"前端怎么写"这个问题的答案给了，但"测的是谁"这个问题的答案没变。**

## 1.6 专业测速原理对标（全球网测 / 泰尔网测 / Cloudflare）

### 1.6.1 先纠正一个信息：哪个才是"全球网测"

**"全球网测"是中国信息通信研究院（CAICT）官方的 App**，由信通院产业与规划研究所自主研发，2022-11-30 上线，前身是 2016 年的"移动宽带测速"App；iOS 版 2023-02-03 上线，2026-02 已迭代到 v4.4.6。免费、无广告、承诺不后台自启。核心能力是 5G/千兆测速、宽带速率评价、用户上网感知测评、国际访问体验测试。

同一体系里还有 **"泰尔网测"**（信通院泰尔系统实验室研发），公开介绍把技术口径写得更细，可直接作为原理依据：

| 泰尔网测公开描述 | 出处 |
|---|---|
| 下载、上传、**延迟、抖动**等专业指标 | 中国工信新闻网 2021-01-28 |
| **智能优选算法**，从全国 400+（商店页写 500+）测速节点合理选择服务器 | 同上 / 微软应用商店 |
| **支持多种测速协议** | 同上 |
| 单次测速 **30 秒内完成** | 微软应用商店 |
| 道路测试、视频测试（VMOS 主观体验）、网页测试（DNS 解析/连接/加载时延） | 中国工信新闻网 |
| 结果留存、可导出 | 同上 |

**⚠️ 需要提醒**：搜索时会出现 `quanquwangce.com.cn`、`quanqiuwangcesu.asia` 这类同名站点。它们**不是官方**——页面没有备案号、没有开发单位、没有真实 App 下载链接，文案是通用模板（"覆盖六大洲 200+ 节点""50~150MB 流量"）。**不要把这两个站的内容当技术依据**。本文只引用信通院/泰尔实验室可追溯的公开描述。

另外网上流传的 "YD/T 3326-2023《移动通信网络服务质量测量方法》" 与"全球网测完全对齐该标准"的说法，只出现在 SEO 内容站，**没有查到一手出处，不予采信**。

### 1.6.2 专业测速引擎的硬参数（Cloudflare 官方开源实现）

专业测速和"并发下载刷流量"的差别，靠 Cloudflare 官方 `@cloudflare/speedtest` 引擎可以精确定量（这就是我们节点清单里 `speed.cloudflare.com/__down` 背后的引擎）：

| 机制 | 参数 | 含义 |
|---|---|---|
| **爬坡（ramp-up）** | 默认序列：`latency×1 → download 100KB×1 → latency×20 → download 100KB×9 → 1MB×8 → upload 100KB×8 → 1MB×6 → download 10MB×6 → … → 250MB×2` | 逐级增大请求块，克服 **TCP 慢启动**，不是一上来就满并发 |
| **自适应停止** | `bandwidthFinishRequestDuration = 1000ms` | 某一档单请求耗时达到 1 秒，就不再做更大的档，避免大文件白跑 |
| **带宽取 P90** | `bandwidthPercentile = 0.9` | ⭐ **不是平均值，也不是峰值**，取 90 分位代表"可持续吞吐" |
| **延迟取 P50** | `latencyPercentile = 0.5` | 中位数，抗离群 |
| **丢弃无效样本** | `bandwidthMinRequestDuration = 10ms` | 太短的请求不计入 |
| **扣掉服务端时间** | `server-timing` 头 / `estimatedServerTime` | 只算链路时间，不算服务器生成数据的时间 |
| **负载延迟** | `measureDownloadLoadedLatency = true`，每 400 ms 一探，留最近 20 点 | ⭐ 下载跑满时同时测延迟，用于识别 **Bufferbloat**（缓冲膨胀） |
| **丢包** | 独立 TURN/UDP 探测 | 与带宽测试分开 |

### 1.6.3 用户口径纠正：这是**两个独立功能**，不是同一功能的两副面孔

> 用户明确："**流量消耗器和测速是两个东西。**"

v2 之前把 B 当成"带保护罩的流量消耗器"，再往上补 P90、爬坡、负载延迟，想把它"改造成测速仪"——**这个方向是错的**。两者目的相反，硬合在一个页面、一套参数、一个结果区里，只会出现"想测个速，结果跑了 1 GB 流量"这种事故。

**必须分开，各自独立：**

| 维度 | ① 测速（Speed Test） | ② 流量消耗（Traffic Burner） |
|---|---|---|
| 用户要的答案 | **"这张卡现在能跑多快"** | **"我已经用掉多少流量"** |
| 停止条件 | **自动**：达到测量可信度即停 | 手动停 / 流量上限 / 时长上限 / 过热 |
| 默认时长 | 15–30 秒（对齐泰尔的 30 秒内） | 300 秒，可调，允许"不限" |
| 默认流量上限 | **150 MB**（对齐 50–150 MB 量级） | 1 GB，可调到 10 GB |
| 并发策略 | 爬坡到饱和（逐步加线程） | 固定 N 线程，稳定持续 |
| 结果主数 | **P90 下行带宽** | **累计消耗流量** |
| 副指标 | 峰值、空闲/负载延迟、抖动、节点 RTT、测量可信度 | 平均速度、实时速度、运行时长、峰值 |
| 慢启动处理 | 丢弃前 3 秒样本 | 不处理（不关心结论精度） |
| 负载延迟 / Bufferbloat | 要 | 不要 |
| 节点选择 | 按 RTT 自动优选 | 用户手选 / 按流量轮换 |
| 结果留存 | 本次会话最近 3 次，便于对比 | 不留，只看当前会话 |
| 误触成本 | 低（≤150 MB 且自动停） | **高（可达数 GB，必须二次确认）** |
| 二次确认 | 不需要 | **必须写清"将使用移动数据，上限 X GB，约 ¥Y"** |

**共享的只有底层**（同一个服务、同一套 curl 编排、`rx_bytes` 采样、URL 白名单、三道保护、busy 守卫、节点清单）。**参数、停止逻辑、结果语义、页面、确认流程全部各自独立。**

### 1.6.4 分离后的接口设计

**保留一个任务槽**：设备同一时刻只能跑一个任务，`start` 带 `mode` 参数（`speed` / `burn`），`status` 回带 `mode` 供前端选渲染模板。理由：两个任务抢同一条 `wwan0`，`rx_bytes` 无法归属；用一个槽 + 全局 busy 守卫最自然，也和 `service.c:123-129` 的既有约定一致。

```
start  {mode, node, threads, max_bytes, max_seconds, limit_kbps}
status → {mode, running, ..., result: <按 mode 不同结构>}
stop   {}
nodes  {mode}   # speed 返回带 rtt_ms 排序；burn 返回原顺序
```

- `mode=speed` 忽略用户给的 `max_bytes` / `max_seconds` 之外的长时长参数，强制用测速默认（30 s / 150 MB），**且到点自动停**
- `mode=burn` 允许大上限，但三道保护一个不减
- 前端两个**独立 tab**：`测速` 与 `流量消耗`，各自一套参数区和结果区，不共用同一个"开始"按钮

### 1.6.5 测速模式专属的四条口径（只作用于 ①，不污染 ②）

1. **三个速度数分开**：`平均速度`（总流量÷总时长）、`P90 带宽`（测速主值，稳定期采样 90 分位）、`峰值`（最大单秒采样）。全程平均会被慢启动拉低、峰值会被突发抬高，都不能当"能跑多快"的答案。**流量消耗模式不显示 P90**，只显示累计量与平均速度。
2. **丢弃前 3 秒样本**：设备 CPU 弱、curl 启动有先后。不照搬 Cloudflare 的 14 档爬坡（对嵌入式太重），用固定剔除窗口近似。
3. **测速期间同时测"负载延迟"**：每 1 秒 `ping -c1 -W1 223.5.5.5`，与空闲延迟对比。跑满时延迟从 25 ms 涨到 300 ms 即为 Bufferbloat，给一条黄字提示。
4. **节点按 RTT 优选**：`nodes` 对候选各发一次 `curl -o /dev/null -r 0-0 -w '%{time_connect}'`，选最低者作默认。流量消耗模式保持用户手选与按流量轮换。

**不采纳的**：14 档爬坡（CPU 与流量开销）、TURN 丢包探测（§4.3 已定首版不做上行/主动探测）、AIM 场景评分、300 条历史记录（rootfs 只读，§9-6 已定不留存）。

### 1.6.6 温度数据源顺带核实（纠正一处旧写法）

之前文档把温度笼统写成 `status.thermal`。核实后：**`thermal` 挂在 `udx.status` 上，不是 `udx.cellular.status`** —— `packages/udx-device/src/device.c:311` 用 `sysfs_array("/sys/class/thermal/thermal_zone*", 0)` 组装，`:219` 把 sysfs 的毫摄氏度 `/1000` 成 `temperature_c`；`hardware2.js:520` 消费的 `d.thermal` 来自 `udx.status`。

因此 §4.5 的过热保护**不需要走 ubus**，守护进程直接扫 `/sys/class/thermal/thermal_zone*/temp` 取最大值即可，与硬件页同源、少一次跨进程调用。`wwan0` 也已双重确认（`network.c:24`、`proto/udx.sh:16`）。

## 2. 实现形态对比（A1 / A2 / B / C）

### 方案 A：纯浏览器（照抄参考站）

在 LuCI 页面里用 `fetch` 并发下载，前端自己算速度。

| 维度 | 评价 |
|---|---|
| 后端改动 | **零** |
| 实时性 | 最好（数据天生在浏览器里） |
| 测的是谁 | ⚠️ **PC → 管理口 → wwan0 的最慢一段** |
| 能否后台跑 | ❌ 关标签页就停 |
| 流量算谁的 | 走 NAT 才算卡的；不走 NAT 完全测错 |
| 准确度 | **不合格**（管理口是瓶颈，见 §3.2） |

**只有在一种情况下可用**：当作"用户体验测速"——模拟"我拿手机连上这个壳，实际能跑多快"。这个数对用户有意义，但它**不是卡的能力**，不能标成"网速"。

管理口是 USB SuperSpeed gadget（`gadget.sh:323` `max_speed = super-speed`），但 UDX710 的 DWC3 在 USB3 上有已知 LPM 问题（历史上专门有过 `fix/usb3-lpm` 分支）。**实际能跑多少必须实测**，这一点见 §3.2。

### 方案 B：设备本地 curl 任务（推荐）

设备上跑 `curl`，显式绑 `wwan0` 出口，数据写 `/dev/null` 不落盘。前端下指令、轮询进度。

| 维度 | 评价 |
|---|---|
| 后端改动 | 一个服务 + 一个 ubus 对象 |
| 测的是谁 | ✅ **模组本身**（不受管理口影响） |
| 实时性 | 轮询 1 秒，够用 |
| 能否后台跑 | ✅ 关页面继续跑 |
| CPU 开销 | ⚠️ curl 拷贝 + TLS 解密要吃 CPU，**可能是新瓶颈** |
| 准确度 | **取决于 CPU**，见 §3.1 |

### 方案 C：A + B 双模式

两个都做，让用户选"测卡的能力"还是"测实际体验"。

**不推荐首版做。** 两套计数逻辑、两个结果语义，用户会问"为什么两个数差三倍"，解释成本高于收益。等 B 稳定后再说。

### 对比

方案 A 现在有两种落地方式：**A1 自己写简化版前端**，或 **A2 直接部署 §1.5 那个 FlowLoss 打包页**。A2 比 A1 便宜且功能强，所以如果走浏览器路线，没有理由自己写。

| 管理口不成为瓶颈 | ❌ | ❌ | ✅ | ✅ |
| 零后端 | ✅ | ✅ | ❌ | ❌ |

| 曲线 / 轮换 / 限速 / 上限 | 要自己写 | ✅ **现成** | 要自己做 | ✅ |
| 风格与 LuCI 一致 | ✅ | ❌ Naive UI 蓝色风 | ✅ | 部分 |

| 复杂度 | 低 | **最低** | 中 | 高 |
| 工作量 | 1.5 人日 | **0.5 人日** | **5.5 人日** | 7.5 人日 |

## 3. 两个必须先验证的瓶颈

这两件事**不验证就排期，等于赌博**。都写进 M0。

### 3.1 瓶颈一：CPU 会不会先于网络跑满

`curl` 下载到 `/dev/null` 看似无成本，实际每条连接都在做：

- TCP 数据从内核态拷到用户态（SIPA 有硬件加速，但只在特定路径）
- TLS 解密（公开测速节点几乎全是 HTTPS）
- HTTP 分块解析

UDX710 是大小核结构，管理口相关的中断已经被 `gadget.sh` 手工绑到 CPU0/CPU1 上（`g_affinity_*` 那段注释写得很清楚）。**测速进程如果和它们抢同一颗核，结果会互相拖累。**

**M0 实验（0.5 人日，必须做）**

在真机上跑三组，每组 20 秒，记录 `wwan0` 的 `rx_bytes` 增量：

```sh
# 组 1：单线程 curl，HTTPS
curl -sS -o /dev/null --interface wwan0 --max-time 20 \
     --write-out '%{speed_download} %{size_download}\n' \
     'https://<大文件节点>?r='"$$"

# 组 2：4 线程并发（后台起 4 个）
for i in 1 2 3 4; do
  curl -sS -o /dev/null --interface wwan0 --max-time 20 \
       "https://<大文件节点>?r=$i$$" & done
wait

# 组 3：同上，但用 http://（如果能找到不跳转的节点）
```

判定：

| 结果 | 含义 | 后续 |
|---|---|---|
| 单线程 ≥ 400 Mbps | CPU 不是瓶颈 | 方案 B 直接成立 |
| 单线程 200–400，4 线程明显更高 | 单核受限，多线程可补 | 默认 4 线程 |
| 4 线程仍 < 200 | **CPU 或 SIPA 路径受限** | 测速功能价值大降，需重新评估 |

**这一组数据也顺便回答"这台设备到底能跑多快"**，对整机验收同样有用。

### 3.2 瓶颈二：管理口到底多少带宽

如果 §3.1 得出"卡能跑 800Mbps"，而管理口只能跑 300Mbps，那么任何从 PC 发起的测速都会封顶在 300。

**验证方法**：PC 侧用 iperf3（镜像里已经有 `iperf3`）跑管理口对打：

```sh
# 设备侧（假设同为 192.168.88.1）
iperf3 -s
# PC 侧
iperf3 -c 192.168.88.1 -t 20 -P 4
```

这个数一旦测出来，就永久记录在文档里——以后所有"为什么只有 300Mbps"的疑问都有答案。

**§1.5 之后，这个数字的权重变了：它现在是 A2 与 B 之间的唯一判据。**

因为 A2（直接部署 FlowLoss）只差这一个前提就能成立，而这个前提是可以一次测定的：

| 管理口实测 | 判定 | 结论 |
|---|---|---|
| **≥ 600 Mbps** | USB3 正常 | **选 A2**。5G 绝大多数场景跑不满它，浏览器测速结果可信，成本 0.5 人日 |
| 250–600 Mbps | 临界 | A2 只能当"体验测速"，**不能标成"网速"**。要准确就必须走 B |
| **≤ 200 Mbps** | 掉到 USB2 或 LPM 严重降速 | **A2 直接不可用**，无论怎么改都会封顶。必须 B |

判据的来源：USB3 SuperSpeed 理论 5 Gbps、实测常见 2–3 Gbps，正常远高于 5G；一旦这个数只有 200 多，几乎只能是链路上协商成了 USB2（480 Mbps 理论、实测 280–320 Mbps），那就是 DWC3 的 LPM 老问题复发——历史上专门开过 `fix/usb3-lpm` 分支就是为它。

**所以 M0 实验的顺序要改**：先测管理口（3 分钟，一条 iperf3 命令），再决定要不要做 §3.1 那个 CPU 实验。如果管理口就不够，CPU 再快也没意义。

顺带说明：**方案 B 完全绕开这个瓶颈**，因为流量从 `wwan0` 直接进 `curl`，不经过 `uncm0`。

## 4. 后端设计（方案 B）

### 4.1 进程模型

新建独立包 `udx-speedtest`，不塞进 `udx-cellular`。理由：`udx-cellulard` 是 AT 控制器，职责单一（`service.c` 里连一个 `sleep` 都要谨慎）；测速是纯数据面操作，混进去会破坏边界，也影响 M0.5 的重连修复。

```
/usr/sbin/udx-speedtestd          常驻，ubus 对象 udx.speedtest
/etc/config/udx-speedtest          节点列表、默认参数、上限
/etc/init.d/udx-speedtest          procd 托管，respawn 开（这个是纯粹的读网络，崩了直接重启没副作用，和 udx-cellulard 的处境不同）
```

ubus 方法：

| 方法 | 参数 | 返回 |
|---|---|---|
| `status` | — | `{running, speed_now, avg, peak, total_bytes, elapsed, latency_ms, samples[], node, error}` |
| `start` | `{node, threads, max_bytes, max_seconds, limit_kbps}` | `{accepted, busy}` |
| `stop` | — | `{accepted}` |
| `nodes` | — | 可用节点列表（按运营商分组） |

**`start` 必须带 busy 守卫**，第二次调用返回 `{accepted:false, busy:true}`，和 `service.c:123-129` 的既有约定一致。

### 4.2 数据从哪来

**不用 curl 自报的速度，用网卡计数器。**

```sh
cat /sys/class/net/wwan0/statistics/rx_bytes
```

每 500 ms 读一次，差值就是瞬时字节数。理由：

- curl 的 `%{speed_download}` 只统计应用层收到的字节，**漏掉重传**
- 运营商计费按更底层，`rx_bytes` 更接近真实消耗
- 多线程时不必汇总 N 个进程的输出

`wwan0` 是唯一承载接口（`network.c:24` 写死 `ifname: "wwan0"`），不会漏计其他接口。

**但有一个待验证项**：`wwan0` 走 `CONFIG_WWAN` + SPRD SIPA，`rx_bytes` 统计的是解聚合后的 IP 层还是更底层，需要实测对比（见 §9-3）。若统计偏小，运营商账单会比页面显示的略高，通常是 3–6% 的头开销差。

**上行**：`tx_bytes` 同理，但首版不做上行测速（§4.3）。

### 4.3 为什么首版不做上行

上行要往公网**写**数据，需要可写的接收端点。参考站全是纯下载，正说明这一点——公共节点不提供上传。

能凑合用的大概只有 `https://speed.cloudflare.com/__up` 这类，但它存在两个问题：

1. Cloudflare 在国内的可达性和速度不代表运营商链路
2. 上传会把数据真的写到对方服务器（虽然丢弃），有滥用嫌疑

**结论**：首版只做下行。上行留给"高级"里的 `iperf3` 模式——用户如果有自己的服务器，`iperf3 -c <host> -R` 能给出可信的上行，且镜像里已经装了 `iperf3`（`configs/openwrt-main.config:28`）。这条路不占默认工作量。

### 4.4 安全（三条硬约束）

1. **只允许 `http://` 和 `https://`**
   `curl` 支持 `file://`，不加限制等于把 `/etc/shadow` 变成可读的测速"节点"。必须显式 `--proto =http,https`。
2. **禁内网目标**
   拒绝解析到 `127.0.0.0/8`、`10/8`、`172.16/12`、`192.168/16`、`169.254/16`、`::1`、`fc00::/7` 的地址。否则这个功能就是个 SSRF 探针，能打内网设备、能打自己 `127.0.0.1:80`。
3. **并发上限 8，单连接超时 30s**
   线程数不设上限等于给自己开一个 DoS 入口。

### 4.5 三道保护（这是重点）

这不是普通功能，**每次误触都是真金白银**。

| 保护 | 设定 | 触发后 |
|---|---|---|
| **流量上限** | 默认 1 GB，可设 100 MB–10 GB | 达到立即 kill 所有 curl，页面标黄"已达上限" |
| **时长上限** | 默认 300 秒，可设 30–1800 秒 | 同上 |
| **温度保护** | SoC 或基带 > 70 ℃ | 立即停，页面标红"温度过高已中止" |

温度读 `status.thermal` 已有的数据（`hardware2.js` 在用），不新增采集。

**二次确认必须写清楚数字**：不是"确定要开始吗"，而是"将使用移动数据，上限 1 GB，按 1 元/GB 约 ¥1.00"。用户点下去之前要知道花多少。

### 4.6 与现有系统的互斥

| 场景 | 处理 |
|---|---|
| 测速中用户点「应用变更」 | 拒绝，提示"测速进行中，请先停止"（改 APN/制式会断流，测出来的数没意义） |
| 测速中用户拔卡 | 测速自动停，记一条"因 SIM 移除中止" |
| 测速占满带宽时 telemetry 响应变慢 | ⚠️ **可能让 `service.c:110` 的 `stale = age > 35` 误判**，导致概览突然出现"数据可能已过期"黄条。**这是真实副作用**，见 §5.2 |

**两个 tab 都不显示对方的主指标**：测速页不显示"累计 312 MB / 1 GB"这种进度，流量消耗页不显示 P90 和负载延迟。共享的只有同一个 busy 守卫——一个在跑，另一个的按钮明确显示"已有任务在运行（测速/流量消耗）"，而不是变灰让人猜。

### 5.3 为什么不做"定时任务"

参考站的 `llxs.youvip.cc` 支持"每天 22:00–06:00 自动跑"。**这个功能不能做**：

- 半夜自动跑光几个 GB，用户第二天才发现账单
- 和"达量限速"叠加时，会在用户不知情时把卡跑进限速状态
- 无人值守的长时间大流量，最容易被运营商风控标记

如果确实要，做成"单次定时"（跑完自动关），且必须有手机通知。**首版不做。**

### 5.4 实时曲线

LuCI 现有代码里**没有任何图表库**（`hardware2.js` 里搜不到 canvas/svg 绘图）。所以：

- 不引入 Chart.js（多 200KB，且和 Outline 主题的 CSS 变量体系不兼容）
- 自己写 **SVG `<polyline>`**，60 个采样点，1 秒一个点，正好 60 秒窗口
- 逻辑放 `udx.js` 里，和 `SIGNAL_CURVES` 同一层

约 40 行 JS，比引库干净。

### 5.5 全局状态

测速是个会跑几分钟的任务，用户一定会切页。所以：

- 测速进行中时，**所有页面顶部出现一条 2px 的青色细条**（不确定进度条样式）
- 点这条细条回到测速 tab
- 侧边栏「移动网络」项右侧显示一个小圆点

数据来源是 `udx.watch` 的推送（已有机制），不需要新开轮询。

### 5.6 与 §4.6 的 stale 误报怎么处理

测速满载时，AT 的 telemetry 可能变慢，`age > 35` 会触发 `stale=true`，概览会弹"数据可能已过期"。

**处理**：测速期间把 `stale` 的阈值从 35s 临时放宽到 90s，或者直接抑制这条黄条（因为用户知道自己在测速）。我建议**抑制**——在测速进行中，概览黄条改为不显示，并在测速页说明"测速期间状态刷新会变慢"。

这是必须处理的，否则用户会以为设备出问题了。

## 8. 验收

1. 测速中 `cat /sys/class/net/wwan0/statistics/rx_bytes` 的增量与页面显示的"已用"一致（误差 < 2%）

8. 测速跑到中途关掉浏览器标签，1 分钟后重新打开，仍在跑且数字连续
9. 测速期间概览页**不出现**"数据可能已过期"黄条
10. 拔卡后测速在 5 秒内自动停，记录一条"SIM 移除"

## 附：一句话总结

**一句话：设备本机跑 `curl` 从 `wwan0` 出去（已拍板按 B），并且做两个独立功能——「测速」回答"能跑多快"，「流量消耗」回答"用掉多少"，只共享底层引擎，参数、停止逻辑、结果、页面、确认流程全部各自独立。**

参考站源码（`arsnyeon/FlowLoss_SpeedTestPanel`，MIT）找到了，但它是浏览器端工具，测的是"打开页面的那台设备"的链路，绑不了 `wwan0`、读不到温度，所以只借它的引擎算法与节点清单，不整体搬用。专业测速的口径对齐全球网测 / 泰尔网测 / Cloudflare 引擎（P90、爬坡、负载延迟、RTT 优选），**但只作用于测速模式**。

工作量 **7.0 人日**（含 M0 0.5）。C 服务本地编不了，按你指示**用 GitHub CI 交叉编译验证**；但**每次推送触发构建前我会单独通知你确认**，且首次 CI 产物只验编译、不刷机——CI 编过不等于能开机。
