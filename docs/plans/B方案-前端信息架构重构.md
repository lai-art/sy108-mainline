# SY108 前端 B 方案：信息架构重构

> 基于仓库 `lai-art/sy108-mainline` @ `19049a3` 的实际代码。
> 配套样板：`docs/plans/样板-B方案.html`（可点击，含四种故障态演示）。

## 0. 一页结论

把现在**按接口划分的 5 个页面**，改成**按用户任务划分的 6 个页面**：

```
现状                          改后
─────────────────────────     ─────────────────────────────
概览 + 网络控制（表单+23行表）  → 概览（纯读看板，4 张卡）
频段、小区与 APN（4 tab）       → 移动网络（连接/频段/运营商/APN）
（没有落点）                   → SIM 卡（诊断 + 重新识别）★新增
短信（5 tab）                  → 短信（不动）
AT 终端与 IMEI                 → 高级（收口 + 警告条）
硬件与平台（5 面板）           → 硬件（面板化，去 hack）
```

三条贯穿原则：

1. **配置集中、诊断单列、危险收口** —— 改配置只在「移动网络」，看状态和救急在「概览 / SIM 卡」，可能把设备弄离线的东西全在「高级」并且带红条。
2. **一屏只回答一个问题** —— 概览不放任何表单；移动网络的每个 tab 只干一件事。
3. **每次操作都要能说清"做到哪了"** —— 多步变更摊开成分步进度，不确定态与失败态分开表达。

工作量 **9.7 人日**：前端 9.0 + 后端 0.7。**后端那 0.7 人日只用于延时探测（0.5）和 `qos.kind` 字段（0.2）**——QCI 与 AMBR 的数值后端早就在采集（§2.1.1）。不含后端 M2/M3。可拆成 5 个可独立上线的切片，见 §7。

## 2. 六个页面定义

### 2.1 概览（重写）

| 项 | 内容 |
|---|---|
| 目标 | 三秒内回答"现在通不通、信号好不好" |
| 数据来源 | `udx status`（已有）+ `network.interface.wan/wan6 status`（`udx.js:160-185` 已在合并） |
| 组件 | 7 张 KPI 卡 + 最近事件列表 + 3 个动作（明细见下） |
| 不放 | 任何可提交的表单、任何 `readonly` 控件 |
| 空态 | 未注册网络 → 卡片显示"搜索中"，不显示 `—` 一片 |
| 错误态 | `status.stale=true` → 整页顶部黄条"数据可能已过期，上次更新 N 秒前" |
| 不确定态 | 顶部黄条 + 卡片值改显"未知"，**不显示上一次的残留值** |

**7 张卡的明细与数据来源：**

| # | 卡片 | 主值 | 副信息 | 数据来源 | 是否要后端新增 |
|---|---|---|---|---|---|
| 1 | 信号 | RSRP + 等级徽章 | RSRQ / SINR + 取色条 | `status.cellular.cells[]` | 否 |
| 2 | 网络 | 运营商 + 制式 | 频段/带宽、PCI/ARFCN | 同上 | 否 |
| 3 | SIM | 状态 + 槽位 | ICCID 掩码、最近识别时间 | `status.physical_sim`、`status.sim` | 否 |
| 4 | 数据 | 连接时长 | IPv4 / IPv6 地址 | `status.data_session` | 否 |
| 5 | **速率与等级** | Session-AMBR ↓/↑ + **QCI 等级徽章** | QCI 语义、MBR 峰值、IPv4/IPv6 延时 | `status.qos`（**已有**） | ⚠️ QCI/AMBR **零改动**；只有延时需新增 `status.latency` |
| 6 | **整机温度** | 取 SoC / 基带最大值 | SoC、基带分项 + 变色条 | `status.thermal`（`hardware2.js` 已在用） | 否 |
| 7 | **磁盘空间** | 各卷名称 + 占用条 + 容量 | 已用/总量，按占用率变色 | `status.storage`、`status.ubi`（已在用） | 否 |

三条设计约束：

- **温度取 max 不取平均**：平均温会被低温传感器稀释，过热判断要看最热的那个点。卡片主值显示最大值，下面再列 SoC 与基带分项。
- **磁盘按卷分行，不合并**：`overlay` 写满会让配置全丢，`/tmp` 写满只影响运行态，两者混成一个百分比会掩盖前者。只读的 rootfs 单独标"只读"，不用占用率着色。
- **速率卡必须标清"这是网络授予的值"**：卡片底部一行灰字 `网络授予的 Session-AMBR…`。原因见 §2.1.1，不标清楚用户会拿它跟营业厅页面的"签约速率"对账，然后投诉对不上。

**需要后端增量的恰好两处**：

1. **最近事件**——最小实现可先用前端兜住：在 `udx.watch` 回调里 diff 上一次 `status`，本地累积最近 20 条（不落盘、不跨刷新），**0 人日**。要跨刷新保留才需要后端加 `status.events`。
2. **延时**——前端测不了（浏览器拿不到 ICMP），必须后端补 `status.latency = { ipv4_ms, ipv6_ms, at, error }`，每 30 秒探一次；IPv4 探网关 + 一个公网地址，IPv6 单独探（**没有 v6 地址时必须返回 `null` 而不是 0**）。约 **0.5 人日**。

   **速率与 QCI 不需要任何后端改动**，理由见下。

#### 2.1.1 为什么「速率与等级」不用改后端

已核实（不是推测）：

| 事实 | 位置 |
|---|---|
| `AT+CGEQOSRDP` 已在发，每 **300 秒**自动轮询 | `info.c:332`；`telemetry.c:10` 的 `operations[6]` + `intervals[6]=300` |
| 返回值按 TS 27.007 解析成 `cid, qci, gbr_*×2, mbr_*×2, ambr_*×2` | `info.c:359-377`（`qci` 单独入 359 行，`rates[]` 六项在 360-362） |
| 已落到 `status.qos`，含 `qci` 与 `ambr_*_kbps` | `info.c:383` `json_object_object_add(c->status, "qos", …)` |
| 另给了 `qos.downlink_kbps` / `uplink_kbps` 两个 AMBR 别名 | `info.c:378-381` |
| 前端早已在读 AMBR，且已做 `/1000` 换算 | `overview.js:130-133` `qos()` helper |
| **但前端从未展示 `qci`** | `grep -n "qci\|QCI" overview.js` → 零命中 |

所以这张卡是**纯前端工作**：把 `status.qos.qci` 渲染出来 + 加语义表。

**一个必须说清的边界：设备拿不到"签约速率"。**

- AMBR = 网络在 PDP/PDU 会话建立或修改时**授予**的聚合最大比特率（Session-AMBR），模组只能读到这个授予值。
- HSS 里配置的签约速率，设备侧不可见。
- 多数情况下运营商把 Session-AMBR 直接设成等于签约档位，所以两者数值一致；但**达量限速、临时提速率、定向流量包**这些场景下，授予值会低于签约值。
- 因此卡片主标题用「速率」，脚注写明是网络授予值。**不能写成"签约速率"**，否则限速时会被当成 bug 报上来。

**QCI 与 5QI 的坑：**

- LTE/EPC 下叫 QCI，取值 1–9（另有 65–70、75、79–90 等扩展）。
- 5G SA 下同一个位置返回的是 **5QI**，取值 1–255，语义表与 QCI 不同（1–9 大体沿用，65 以上含义分叉）。
- 后端校验是 `integer_text(…, 0, 255, &qci)`（`info.c:351-352`），两种都收；**但字段名仍叫 `qci`**，前端无法从字段名区分是 QCI 还是 5QI。
- 处理方式：徽章只显示数字（`QCI 9`），语义表在 1–9 内通用，超出 9 的显示"扩展等级 N"而不硬套 LTE 语义。
- **已决定加 `qos.kind = "qci"｜"5qi"`**（0.2 人日后端，归入 M2d）。加上之后前端读 `kind` 决定徽章前缀：`qci` 显示 `QCI 9`，`5qi` 显示 `5QI 9`，语义表也按 `kind` 选不同的一套。在 M2d 落地前，前端按"字段缺省即 QCI"处理。

**附带发现一处缺陷（与这张卡直接相关，建议随 M2c 一起修）**

`telemetry.c:46-50` 在检测到 SIM 状态变化时，只把两个任务的重试时间清零：

```c
if (!text_equal(sim, c->telemetry_sim)) {
        snprintf(c->telemetry_sim, sizeof(c->telemetry_sim), "%s", sim ? sim : "");
        c->telemetry_due[0] = 0;   /* modem_info */
        c->telemetry_due[5] = 0;   /* radio_options */
}
```

`operations[6]` 是 `qos_refresh`、`intervals[6] = 300`，**换卡后没有清零**。后果：换一张卡之后，`status.qos`（含 QCI 与 AMBR）最长还能保留**上一张卡的值 300 秒**，而这正是验收第 10 条要查的"拔卡后不残留上一张卡的数值"。

修法很小（`c->telemetry_due[6] = 0;` 一行），但必须做——否则前端无论怎么改都会显示错的值。建议归入 M2c，标注为"后端 3 行以内"。同理 `[2]/[3]/[4]`（serving / neighbors / advanced）也没重置，属同一类问题，一并加。




### 2.2 移动网络（新建，合并原两页）

六个 tab，对应原来散在两个页面的四件事，加上**两个各自独立的新功能**：

| Tab | 内容 | 消费的操作 |
|---|---|---|
| 连接 | 飞机模式、卡槽、网络模式、移动数据、漫游、自动连接 | `policy` `radio` `physical_slot` `network_configure` `connect` `disconnect` |
| 频段与小区 | 频段锁定表 + 服务小区 + 邻区 | `band_lock` `cells_refresh` `serving_refresh` `neighbors_refresh` |
| 运营商 | 扫描结果 + 手动注册 + 自动选网 | `operator_catalog` `operators_scan` `operator_select` `operator_auto` |
| APN | 模板列表 + 编辑 + 启用 | `apn` `apn_templates` `apn_template_save` `apn_select` `apn_template_delete` |
| **测速** | 自动测速，≤30 s / ≤150 MB，主数 **P90 下行带宽** | **新增 ubus 对象 `udx.speedtest`**，`mode=speed` |
| **流量消耗** | 持续耗流，1 GB / 300 s，主数 **累计消耗**，需二次确认 | 同一对象，`mode=burn` |

> ⚠️ **用户明确："流量消耗器和测速是两个东西。"** 两者只共享底层服务、curl 编排、采样、节点清单与一个 busy 守卫；**参数、停止逻辑、结果语义、页面、确认流程各自独立**，不共用一个"开始"按钮。详见 `测速功能方案.md` §1.6.3。样板 `docs/plans/样板-B方案.html` 已按六个 tab 同步。

「连接」tab 的**应用**是全方案最关键的交互改动，见 §6.1。

**这两个 tab 是唯一打破「不新增 ubus 方法」这条约束的地方**——它们需要一个能在设备侧跑并发下载的常驻服务，这是现有 47 个操作里没有的能力。该功能的完整方案、风险与工作量单列在 `测速功能方案.md`（v3，**7.0 人日**），**不计入本文的 9.7 人日**。

放在这里的理由：它测的是网络本身，和「连接 / 频段 / 运营商 / APN」同属一类；放「高级」会被当成调试工具，而它其实是会有真实费用的日常功能。

## 6. 交互规范（六条硬规则）

### 6.1 多步变更必须摊开成分步进度

现在 `overview.js:77-95` 一个 Apply 串 5 个操作，失败只弹一条 toast。改成：

- 点击前显示将要执行的 5 步（策略 → 射频 → 卡槽 → 制式 → 拨号）
- 执行中逐步点亮，当前步高亮
- 失败时停在失败那步并标红，已完成的步骤保持绿色

这样用户能直接说"卡在第 3 步卡槽切换"，而不是"它报错了"。

### 6.2 不确定态与失败态必须分开

`service.c:120` 会产出 `CELL_UNCERTAIN`（"AT outcome uncertain; no automatic replay"）。语义是"**命令发下去了，但没拿到回执，可能已经生效**"。

- 失败 → 红条，文案说"没成功，可以重试"
- 不确定 → 黄条，文案说"**可能已经生效，系统不会自动重试，请先刷新看状态**"

绝不能让用户看到红字就去重试 —— 这类操作重试就是二次风险。

### 6.3 错误文案必须是句子

`overview.js:76` 现在是 `throw new Error(_('SIM slot'))`，界面上就一个词 "SIM slot"。全部改成"所选卡槽不支持切换，请换一个槽位"。

### 6.4 只读态按能力判，不按 URL 判

`maintenance.js:14` 的 `isReadonlyView = !L.hasViewPermission()` 是 URL 决定的，这是已知的疑似越权点。

前端新页面统一走：

```
canWrite = status.supported_operations 包含该操作  &&  session.access 有写权限
```

**必须 fail-open**：只有快照新鲜且明确不含该操作时才隐藏/禁用；快照过期（`stale=true`）时保持可点，交给后端拒绝。否则一次网络抖动就会让按钮全灰。

### 6.5 空态要有引导语

不允许出现一片 `—` 或 `undefined`。每个面板都要定义：无卡 / 未注册 / 无数据 / 快照过期 四种情况下的文案。

### 6.6 颜色阈值必须统一写在一处

概览里现在有五种"变色"：信号等级、温度、磁盘占用、延时、QCI 徽章。前四种的阈值不能散在各个 view 里手写，统一放 `udx.js` 的常量表：

| 指标 | 绿 | 黄 | 红 | 说明 |
|---|---|---|---|---|
| 信号（RSRP/RSRQ/SINR） | 已有 `SIGNAL_CURVES` | 同左 | 同左 | **沿用现有实现，不重定**（`udx.js:69-80`） |
| 整机温度 | < 55 ℃ | 55–70 ℃ | > 70 ℃ | 取 SoC / 基带最大值，不取平均 |
| 磁盘占用 | < 70% | 70–85% | > 85% | 按卷分别算，不合并；只读卷不着色 |
| 延时 | < 60 ms | 60–150 ms | > 150 ms 或超时 | IPv6 无地址时显示"不可用"，**不是 0 ms** |

**QCI 徽章不进这张表**——它不按数值大小分档，而是按"这条承载有没有速率保证"二分：

| QCI / 5QI | 徽章色 | 含义 |
|---|---|---|
| 1–4、65–67、75、82–90 | teal | **GBR**：有最低速率保证，实时业务 |
| 5–9、69、70、79、80 | 中性灰 | **Non-GBR**：尽力而为，这是正常态 |
| 取不到 / 快照过期 | amber | 未知 |

**绝不给 QCI 9 上警告色。** 9 是绝大多数手机上网的默认承载，把它渲染成黄色或红色等于让用户以为一直都在故障。这条是硬约束，验收时会专门查。

同一个数字在不同页面上必须同色，否则用户会以为两台设备不一样。

## 10. 决策与权衡

1. **不推翻重做（否决"前端 C 彻底重做"）**。C 主张新建一套 task-runner 与组件体系，但 `udx.js:48/121-159` 的串行队列已经就是这个东西，重做等于把已有的正确实现再写一遍，多花 6 人日换零功能增量。

2. **不新增 ACL 域**。曾考虑给「高级」单独授权（只有管理员能进 AT 终端）。但 `depends.acl` 是数组，语义（AND 还是 OR）尚未定性，冒然加域可能把所有人都挡在外面。本期先用"危险能力收口 + 红条"约束，ACL 改造等 §6.4 的定性结论出来再说。

3. **保留全局串行队列**。有人会想把队列拆掉、"让不冲突的操作并行"。但后端 `service.c:123-129` 本身就是单实例忙态守卫，前端并行只会不停收到 `busy` 再重试，反而更慢，且会让"第几步失败"变得无法解释。

4. **不做"按权限渲染按钮"**。当前 ACL 是单一域，没有可判定的能力位，按权限渲染只会退化成"人人可见 / 人人不可见"两种假象，比显式禁用更糟。改用 `supported_operations` + fail-open（§6.4）。

5. **保留旧地址而不是硬删**。多写 10 行跳转壳，换掉"升级后老书签白屏"这一整类反馈。

6. **概览的"最近事件"先做前端累积，不落盘**。落盘要加 `boot_id`、要处理重启后失效、要控制文件增长，为 20 条事件不值。若后续要做"故障回溯"再单独立项。

7. **温度取 max 而不是平均**。平均温会被低温传感器稀释，判过热要看最热的那个点。这条会牺牲"整体感"，但换来判定不被稀释。

8. **磁盘按卷分行，不合成一个总进度条**。`overlay` 满会让配置全丢，`/tmp` 满只影响运行态，混在一起会掩盖前者。只读的 rootfs 单独标"只读"，不参与着色。

9. **延时探测只做"能不能通"和"多久通"，不做丢包率**。丢包率要连发多包，30 秒粒度下成本高、噪声大，且在蜂窝网络里波动天然很大，做出来只会误导。
