被否决：**A** 没碰"APN/频段同页""AT/IMEI 同页"两条最痛的事实；**C** 更站不住——它主张的"新增统一 task-runner"其实**已经存在**：`udx.js:48` 串行队列、`:123-156` 的 busy/duplicate 处理、`operation_id`/`broker_id`、`operation_status` 轮询（360s 上限）全都写好了。C 剩下的增量只有视觉组件层，却要付 po 全量重译 + 双主题回归两笔不确定成本。

附带修复（随 B 一起做，不单独计价）：

- `udx.js:198` 的兜底文案写死成短信语境 `_('Some messages were not deleted')`，任何非短信操作失败都会弹这句，应改为通用「操作失败」。
- `overview.js` 三个按钮主次不清：应排成「应用（主）/ 刷新（次）/ 重新附着（第三，二次确认）」，与方案二 C 共用同一个入口。
- `udx.js:113` 设了 `e.uncertain`，但**全仓没有任何消费方**（`overview.js:143` 那个是状态文案，不是错误路径）。而后端 `service.c:120` 确实会产出 `CELL_UNCERTAIN`「AT outcome uncertain; no automatic replay」——最该提醒"别乱重试"的错误，被渲染成一行普通红字。约 3 行修在 `notify()`。
- `udx.js:121` 的 `execute(operation, args)` 没有超时入参，`deadline` 硬编码 360s（`:123`）。重新附着最坏路径约 400s > 360s，会误报超时。加可选第三参、只对该操作传 480s，不动全局值；同时必须配 UI 锁 + 常驻进度——`:48` 的 `queue` 是全局串行，一次长操作会挡住所有 udx 操作。

**只读态裁决**（回应实现侧的提醒）：`overview.js:99-103` 现在点不动，靠的是"没绑 `onclick`"，不是 `reset.readonly`；`readonly` 对 Button 不构成拦截。这条成立，接上 `onclick` 后必须换成实质 `disabled` + rpcd 兜底双保险。

但"无权限就不渲染"这一步**现在不能做**：当前 ACL 是单一域（见诊断第 8 条，`luci-app-udx.json` 一个 ACL 覆盖全部读写），没有可判定的能力位，"按权限渲染"只会退化成"人人可见"或"人人不可见"两种假象。正确顺序是 **ACL 分层在前、按权限渲染在后**。若要在 M3 就做到位，需把 ACL 分层从 M5 提前（+0.5 人日）；否则 M3 阶段接受"入口对能进该页的账号一律可见，靠 rpcd + 二次确认兜底"，并在验收清单里写明这个已知弱点是设计选择而非遗漏。

执行顺序：① menu.d + 标题 + po → ② 拆 hardware2（只读 vs 可写，风险最高优先）→ ③ 拆 at → ④ 拆 cellular → ⑤ ACL 去重与只读态 → ⑥ 真机回归。

## 3. 方案二：SIM 热插拔重识别 + 基带热复位

### 3.1 四层方案对比

| 维度 | A 身份键重识别 | B URC 驱动 | C 射频软复位 | D 基带核复位 |
|---|---|---|---|---|
| 机制 | 比较键 `state` → `(state,iccid,imsi)`；变化时 `invalidate_sim → SFUN=3 → 2s → SFUN=2 → refresh → info_sim_identity` | `transport.c:212-221` 扩分发器，解析 `+CEREG/+C5GREG/+CGEV`，事件优先、轮询兜底 | `disconnect → SFUN=5 → CFUN? → SFUN=4 → 重新注册 → 重建 PDP` | remoteproc stop/start 或 PMU `corereset` |
| 前提 | 全部已有（`modes.c:367-393` 已写好同构序列） | 注册类 URC 已使能（`controller.c:488-489`）；SIM 类 URC **未证实** | AT 通道必须活着 | **`modem_stop()` 直接 `return -EOPNOTSUPP`；`auto_boot=false`、`recovery_disabled=true`** |
| 风险 | 低（秒级断网，需去抖） | 低（at1 会混入 URC 需处理） | 低 | **极高**：复位后 `udx-cellulard` 读 EOF → `session_dead` → 退出，而 init.d 关闭 respawn → **Cellular 永久不自起**，只能物理断电 |
| 可回退 | 是（纯用户态） | 是 | 是 | **否** |
| 工作量 | 2.5–3.5 人日 | 4–6 人日 | 1.5–2 人日 | 16–25 人日 + 内核立项 |

### 3.2 前置门禁：自愈链（P0，必须先于 A/C）

运维线提的硬约束，我核对代码后采纳：**任何能让 `session_dead` 变成真的功能，都必须先有一条不依赖人手的恢复路径，否则不许上。**

三条现成事实叠起来就是"服务一退，设备只能断电或刷机"：`service.c:318-321` 遇 `session_dead` 直接 `break` 退出；`init.d/udx-cellular:11` 明写 procd respawn 关闭；`/run` 是 tmpfs，重启即清。

| 层 | 做什么 | 成本 | 风险 | 备注 |
|---|---|---|---|---|
| L0 | 事件持久化：常态只写 `/run`（不磨损 flash），仅在两个出口 flush 到 `/etc/udx-cellular/events.log`——`service.c:318` 的 `session_dead` 分支与 `run()` 主循环退出前；并加进 `keep.d`（现在只保留 `requests/` 与 `sms.json`） | 低 | 无 | 首发必做，唯一的"死因证据" |
| L1 | 进程内 AT 重连。**不是 30 行**：`transport_reopen()`（`transport.c:398-425`）只重开 `t->fd`（at1），**从不重开 `t->urc_fd`**（at0，`transport.c:453`）；`session_dead` 4 处置位（`transport.c:30/206/237/340`）**从不复位**，而 `transport_admit()`（`transport.c:21-24`）**第二检就是 `session_dead` 直接返回错误** → "只改 service.c 的 break"连 reopen 都过不去；`wwan_fd` 找一次就缓存。另：`service.c:318` 之外还有 6 处 `!poisoned` 守卫都不看 `session_dead`，恢复期间 worker 照样打 AT。实为 60–90 行 + **P0–P6 七项前置** | 高 | 高 | **单列 M0.5，并作为编译前硬卡点**，不与 A/C 同版本 |
| L2 | stale 探针 → 自动 `renew wan` | 低 | 低 | 链路在 proto 层其实完整（`proto/udx.sh:9 renew_handler=1`、`:34 proto_udx_renew`），缺的是**触发者**：`:6-8` 的 `no_device=1` + `no_proto_task=1` 让 netifd 没有 l3 设备事件，不会自触发。**且 renew 不救基带**：`cell_network_setup`（`network.c:221`）只记意图并 `drive()`，不碰 AT |
| L3 | procd respawn | 极低 | 有 | 必须是**独立 procd 实例**（观察者不能放在会死的进程里），用 `ubus list udx.cellular` 判存活 |

**新发现的"假绿"故障态**：`read_notifications()` 在 `urc_fd < 0` 时直接 `return 0`（`transport.c:196-197`），at0 缺失被当成"没有通知"而不是错误 → `uptime` 继续推进、`snapshot_age` 不涨、`stale` 恒 `false`、`available` 恒 `true`。也就是说 **at1 活着、at0 死了时，L2 的判据完全失效**。建议补一个 `urc_age` 字段，但**只作诊断字段、不进 `available` 判据**——空闲期本来就长期没有 URC，并进判据会让健康设备大面积误报，变成新的抖动源。

回滚闸门：新增 uci 开关 `allow_reset`，**默认 0**。只有 L0 落地 + L2 能让失败可见 + T1–T6 验收通过，才允许上复位类功能。**L1 作为独立里程碑，不进 P1**。

验收（必须真机跑，agent 不代跑）：T1 拔卡 → T2 插回 → T3 换 READY 卡 → T4 强制 `session_dead`（判定用机制论证，procd 不看退出码）→ T5 重启后设置不丢 → T6 远程 `renew wan`，**只验"失败可见"，不宣称恢复 IP**。

可推演性分级（避免把"纸面推演"当"已验证"）：**T1、T3 已由代码推演完成**（`controller.c:435-452` 的 `text_equal` 比较键 + `modes.c:367-393` 的已有序列）；**T2a、T5 必须有机器**（硬件未知件 + flash 断电时序无法推演）；**T2 已作废、拆成 T2a/T2b**；T4、T6 可在设备上脚本化。机器只有用户那一台，这三项在他跑之前，M2 的实测结论一律标"未验证"。

T7 所需的"无受控注入手段"**已从源码证实**，证据链可直接复现：`linux-udx710@14658d97`（与 `manifests/kernel.json` 锁定的 commit 完全一致）→ `drivers/soc/sprd/modem/sipc_v2/sipc_wwan.c`（blob `75ae597f`）`:507` 为 `.suppress_bind_attrs = true`，加上 `config-7.3:463` 的 `CONFIG_SPRD_SIPC_WWAN=y`（内建）。设备侧再执行一次 `ls /sys/bus/platform/drivers/ | grep -i sipc` 只是**抽检内核实现与源码是否一致**，不再作为 L1 的验证路径。同一提交上 `sipc.c:392`、`spipe.c:358`、`spool.c:513` 也都是 `suppress_bind_attrs = true`，而 `compatible = "sprd,udx710-wwan-at"` 正是 `find_wwan()` 匹配的 AT 口驱动 —— 所以设备侧注入是**结构上不可能**，不是"还没找到办法"。

> **方法论提醒（本次踩过）**：本地 `linux-udx710` 工作区停在 `606233b6`，与锁定的 `14658d97` 不是同一棵树——该提交下 `sipc_v2/` 里根本没有 `sipc_wwan.c`。核内核事实必须 `git show 14658d97:<path>` 或 `git grep <commit>`，**不能直接读工作区**，否则会得出"文件不存在"的错误结论。

### 3.3 推荐：本期 A + C，B 放 P2，D 不做

- **A** 解决"换卡认不出"这个真痛点，且复用 `modes.c` 已有序列，不新增 AT 命令、不新增 ubus 方法。
- **C** 把 `overview.js:99-103` 那个 `readonly` 的「Restart modem」占位按钮变成真入口：「重新附着」+ 二次确认 + 回显（cfun / 注册态 / IP）。**与 A 共享同一套重识别函数**，避免两套状态机。

C 的两条硬性实现约束（不满足就不算完成）：

1. **不许出现"假成功"**：`controller.c:311-323` 在 busy 时会走 `background_deferred` 把事务推迟到下一轮。这种中间态必须渲染成 `uncertain`；**不能出现"UI 说成功、重启后状态才对"**。范围收窄为**只在重新附着这条路径读 `uncertain`**，不改全局 `notify()`——全局改属产品决策，不在方案轮夹带，登记为技术债待 M5 评估。
2. **配置守卫必须显式返回错误**：`controller_radio_reattach` 若在 `!radio_enabled(c)` 时被调用，必须返回明确错误（如 `CELL_INVALID`），不能返回 ok——否则与"radio off 策略"（`service.c:291`）自相矛盾。
3. **验收只认 `result.connected`**，不认 `ip` 或 `leased`：检查 `proto/udx.sh` 只做 JSON 中转，**从不发 `proto_init_update`/`proto_send_update` 给 netifd**，所以 `interface up` 与"链路真通"是两件事（`proto_udx_teardown` 才发 update）。
4. **能力清单不做新字段**：`status.supported_operations` 已经发布（`controller.c:297`），前端直接读它 + `session.access`，比新增 `capabilities` 少写 C 且不会漂移。读法**必须 fail-open**：只在"快照新鲜且明确不含该方法"时隐藏入口；快照超龄/字段缺失/取不到时照常渲染，只在二次确认里提示"当前固件可能不支持"。理由：把"能力缺失"伪装成"功能不存在"，只是换了个时间维度。
5. **失败态分两档样式**：`uncertain`（仅 `transport.poisoned` 时出现，`service.c:263-272`）用 warning「结果未知，设备可能已生效，请刷新确认」；`failed` 是明确业务失败，用 error「操作失败」。合并两者会诱导用户重复操作，进 M3 验收清单。
- **B** 先用 A 兜底保证正确性，B 只做降负载；SIM 类 URC 必须先抓到原始行才允许接。
- **D 明确不做**：给现场的"最后手段"现阶段就是整机重启，不要伪装成基带复位。

## 8. 决策与权衡

1. **采纳架构师对底稿的纠正**（10s 轮询本就存在）。我给的"没有轮询"是错的，方案 A 的定义随之改写，工作量从"新增轮询"降到"改比较键"。这是本次唯一的事实性冲突，以代码为准。
2. **前端矩阵与推荐不一致时，按"收益优先"重排权重**，不掩盖矛盾，也不和稀泥。
3. **D 不因"听起来最彻底"而保留**：`modem_stop()` 是 `-EOPNOTSUPP`、`recovery_disabled=true`、`udx-cellulard` 无 respawn，三条叠起来意味着"复位成功也可能把设备弄成需要断电"。也**别指望先在 Recovery 里试**：`config-recovery:28-29` 是 `# CONFIG_WWAN is not set` + `# CONFIG_SPRD_SIPC_WWAN is not set`，Recovery 系统里根本没有 AT 端口。D 真要验证只能在主系统 + 串口，失败即整机断电。
4. **分支治理按 B 而非 C**：C 的远端改名是"推新名 + 删旧名"两步非原子，断网即出现两份，垃圾只是换了前缀。
5. **采纳"自愈先于复位"的硬门禁**：不是保守，是代码决定的——`session_dead` 会直接 `break` 退出、respawn 关闭、`/run` 重启即清，三条叠起来意味着"复位成功也可能把设备弄成得断电"。所以 M0 排在 M2/M3 之前，不是可选优化。
6. **回滚闸门用 uci `allow_reset`（默认 0），不用编译期开关**：编译期开关要回滚就得刷机，与"远程止血"的目标正好相反。
7. **把 `e.uncertain` 这条"沉默的错误"拉进本期**：后端已经明确会产出 `CELL_UNCERTAIN`，前端却当普通错误渲染，用户会照着红字继续重试——在只做一次 AT 事务的场景里这是会放大故障的。3 行代码，不单独计价。
8. **主动削范围**：`status.sim_reidentify` 不落盘、不加 boot_id、不留历史，省 0.5 人日；理由是重启即清 `/run`，收益低于复杂度。

### 9.1 T2a —— renew 链路能否把 `wan` 重新挂上（不需任何新代码）

验的目标只有一个：`ifdown wan` 之后 `ifup wan`，账号健康时地址能不能自己回来。**这是 `renew` 链路唯一不写代码就能验的一条**，也是 M1 的地基。

```sh
#!/bin/sh
# t2a.sh —— 在设备上跑：sh /tmp/t2a.sh
set -u
say() { echo; echo "===== $* ====="; }

say "0. 基线（此时必须是 available=true、stale=false、有 IPv4）"
ubus call udx.cellular status '{}' | jsonfilter -e '@.available' -e '@.stale' -e '@.snapshot_age_seconds'
ubus call network.interface.wan status | jsonfilter -e '@.up' -e '@.device'
ip -4 addr show wwan0 2>/dev/null | grep -w inet || echo "!! wwan0 上没有 IPv4，先修好再往下跑"

say "1. 健康态重挂：ifdown → ifup"
ifdown wan; sleep 2
ifup wan; echo "ifup 返回码=$?"
# ifup 立刻返回（proto_udx_setup 只登记意图），真正装地址靠 daemon 的 2s 重试定时器
i=0
while [ $i -lt 15 ]; do
	i=$((i+1)); sleep 1
	if ubus call network.interface.wan status | grep -q '"address"'; then
		echo "OK: IPv4 在 ${i}s 内回来"; break
	fi
done
[ $i -ge 15 ] && echo "FAIL: 15s 内没回来 —— 健康态都挂不上，M1 之前先查 notify_proto"

say "2. 阶梯：模组侧不可用（此处需人工拔卡，脚本只观测）"
echo "现在拔掉 SIM，等 40s 让快照过期，然后回车继续"; read -r _
ubus call udx.cellular at_debug '{"command":"AT+CPIN?","timeout":10}' | jsonfilter -e '@.response' -e '@.success'
ubus call udx.cellular status '{}' | jsonfilter -e '@.available' -e '@.stale'

say "3. 假成功验证（T2b 的证据）"
ifup wan; sleep 8
ubus call network.interface.wan status | jsonfilter -e '@.up'
ip -4 addr show wwan0 2>/dev/null | grep -w inet \
	&& echo "有地址（少见，记录现象）" \
	|| echo "无地址，但 ifup 早已 accepted —— 这就是 T2b 要抓的假成功"
```

判读标准：

- **第 1 步回来 = renew 链路是通的**，M1 只需补"何时触发"和"失败可见"，不用重写 proto。
- **第 1 步不回、但 `ifdown/ifup` 日志里 `network_setup` 返回 `accepted:1`** → 问题在 `drive()`/`notify_proto`（`network.c:136-158`），不在 AT，也不在 renew。
- **第 3 步 `accepted:1` + 无地址** → 假成功成立，T2b 必做。

### 9.3 T5 —— busy 守卫必须挡住第二次调用

验 `service.c:123-129`：第一个操作在跑时，第二个**排队型**操作必须立刻回 `{accepted:false,busy:true}`，而不是排队、不是阻塞。

```sh
#!/bin/sh
say() { echo; echo "===== $* ====="; }

say "1. 开窗：后台起 operators_scan（只读长操作）"
ubus call udx.cellular operators_scan '{}' > /tmp/t5.scan.json 2>&1 &
sleep 2

say "2. 探针：此时发 refresh，期望 accepted=false / busy=true"
ubus call udx.cellular refresh '{}' | jsonfilter -e '@.accepted' -e '@.busy' -e '@.error'

say "3. 对照：status 应当照常返回（它绕过 busy 守卫）"
ubus call udx.cellular status '{}' | jsonfilter -e '@.available' -e '@.snapshot_age_seconds'

wait
say "4. 长操作的最终回执"
jsonfilter -e '@.accepted' -e '@.id' /tmp/t5.scan.json 2>/dev/null || cat /tmp/t5.scan.json
```

判读标准：

- 第 2 步必须是 `false / true / Another cellular operation is running`。若回 `accepted:true`，说明**这台设备上根本没有忙态串行**，前端那把全局队列（`udx.js:48`）是唯一防线——那就不能拆队列。
- 第 3 步必须正常返回。若 `status` 也被挡，则前端的轮询会在长操作期间整体失联，属于必须修的缺陷。
- 若 `operators_scan` 结束太快（<3s）导致窗口没开成，换 `advanced_refresh`，或对**另一槽位**发 `physical_slot`（会真切卡，先在 `radio_options` 里确认当前 `physical_sim.slot`，测完切回）。

### 9.4 已知坑（省一次白跑）

- `physical_slot` **同槽位是空操作**（`modes.c:302` 早退），拿它当"重新附着"或拿它开 busy 窗口都会失败。
- `network_setup` 的参数是扁平 `{"interface","device","metric"}`；写成 `{"operation":…,"arguments":…}` 会被当成未知方法名落到 `dispatch()`，报 `Invalid request`。
- 拔卡后 `AT+CPIN?` 若回 `+CME ERROR: 10`，`debug_execute` 仍会给 `success:false` + `response` 有内容——**看 `response` 字段，不要只看 `success`**。
- `at_debug` 内部先过 `transport_admit()`，`session_dead` 时直接失败（`transport.c:21-24`），所以它同时也是 L1 状态的探针。
